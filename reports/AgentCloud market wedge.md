# AgentCloud must prove a narrower wedge

**The architecture is sensible; the architecture alone is not a business wedge.** Disposable agent run boxes and independently available artifact homes give users a clear answer to a real lifecycle problem: an agent can stop without taking its website or API down. But Coder and Codespaces already cover much of the workspace and private preview story, while Replit connects agent work to durable publishing. AgentCloud's credible opening is narrower: help *different* coding agents build interdependent components against an organization-controlled development service, then promote known revisions with an accountable handoff. That is a hypothesis about user pain, not an established gap or demand signal. The current AgentCloud repository is a local coordination foundation with service records and seeded replay; it does not yet provision run boxes, enforce a private network, execute Codex or Claude remotely, or publish artifact homes ([Product specification](/Users/nealkotval/hackgt13/PRODUCT.md), [Feature spec](/Users/nealkotval/hackgt13/FEATURE_SPEC.md)).

## The split clarifies ownership, but competitors already use it

A run box should own a working checkout, execution session, logs, and temporary services. An artifact home should own a named release, access policy, health state, and durable data independently of that run. This separation prevents a prototype's mutable filesystem or running process from silently becoming the production system. It also creates a useful promotion point: the user can identify the source revision, verification result, and person or scoped automation that approved publication. **That is sound product and systems design, but an inference about what AgentCloud should build, not evidence of distinctiveness.** Replit explicitly separates its editor's development database from a published app's production database, and its published deployment runs independently of the editor ([Replit development and production databases](https://docs.replit.com/features/data-and-storage/development-and-production), [Replit Publishing](https://docs.replit.com/learn/projects-and-artifacts/replit-deployments)). Vercel similarly treats preview and production as distinct deployment environments, while Render documents deploy health checks and ephemeral service filesystems that require separate durable storage ([Vercel deployment overview](https://vercel.com/docs/deployments/overview), [Render deploys](https://render.com/docs/deploys)).

The proposed “managed home, isolated per artifact” is a good abstraction only if its isolation is real and its scope stays small. An always-on API, static website, and editable wiki have different serving, authorization, backup, and data migration needs. Treating all three as one launch feature would create a hosting platform before proving the collaboration problem. A first release should publish an identified site and API revision through an existing deployment provider, retaining the release lineage and approval record in AgentCloud. Railway already provides environment-private service discovery, and Render provides private services and preview environments; these are credible infrastructure components to integrate rather than rebuild immediately ([Railway private networking](https://docs.railway.com/networking/private-networking), [Render private services](https://render.com/docs/private-services), [Render preview environments](https://render.com/docs/preview-environments)). **The bet is that AgentCloud owns the workflow across agents and releases, not that it invents a new hosting primitive.**

## Coder is a closer rival than the analogy suggests

The Coder/Codespaces comparison works at the run-box layer. Coder provisions workspaces and supports persistent shared staging or QA environments; it also has a self-hosted coding agent that can provision workspaces, run tools there, and delegate work to subagents ([Coder workspace lifecycle](https://coder.com/docs/user-guides/workspace-lifecycle), [Coder persistent shared workspaces](https://coder.com/docs/tutorials/persistent-shared-workspaces), [Coder Agents](https://coder.com/docs/ai-coder/agents)). Coder workspace ports can be shared with authenticated members of an organization, and Coder Desktop exposes running workspace ports through a VPN tunnel ([Coder workspace ports](https://coder.com/beta-docs/user-guides/workspace-access/port-forwarding/)). Codespaces also supports organization-visible forwarded ports and policies to restrict port visibility, though its stopped spaces do not keep processes running ([GitHub port visibility policy](https://docs.github.com/en/codespaces/managing-codespaces-for-your-organization/restricting-the-visibility-of-forwarded-ports), [GitHub codespace lifecycle](https://docs.github.com/en/codespaces/about-codespaces/understanding-the-codespace-lifecycle)). **“Agent workspaces with org access” is therefore too broad a claim to distinguish AgentCloud.**

“Local to the org” needs a precise security promise. An organization-authenticated URL reachable over the public internet and a service with no public ingress are different architectures. GitHub's Codespaces security documentation describes authenticated forwarded ports exposed through internet-reachable URLs; Coder offers both proxied sharing and a desktop VPN tunnel ([GitHub Codespaces security](https://docs.github.com/en/codespaces/reference/security-in-github-codespaces), [Coder workspace ports](https://coder.com/beta-docs/user-guides/workspace-access/port-forwarding/)). AgentCloud's current service registry validates a URL and attributes its registration; it neither probes the endpoint nor enforces a network boundary ([Architecture](/Users/nealkotval/hackgt13/ARCHITECTURE.md)). The proposed private development network must therefore be implemented and tested with an unauthorized request that fails before it becomes a product claim. A hidden link in the dashboard does not meet that promise.

Replit is arguably the stronger comparison for the complete journey. Its task board gives Agent work isolated task copies, dependencies, previews, review, and an apply step; Publishing offers deployment types that outlive the editor, with private access modes ([Replit task board](https://docs.replit.com/features/agent/task-board), [Replit Publishing](https://docs.replit.com/learn/projects-and-artifacts/replit-deployments), [Replit private deployments](https://docs.replit.com/features/publishing/private-deployments)). Devin documents multi-session workflows with progress and resumable stages, and a narrower native path to deploy small standalone apps ([Devin Dynamic Workflows](https://docs.devin.ai/work-with-devin/dynamic-workflows), [Devin app deployments](https://docs.devin.ai/product-guides/deployment-capabilities)). These official descriptions establish feature overlap, not comparable reliability, adoption, or user satisfaction. They do not prove that any rival handles the exact Codex-to-Claude live-service handoff well; equally, their silence does not prove AgentCloud is first.

## The strongest wedge is a verified cross-agent integration loop

The positioning I would test is: **“A private integration workspace where different coding agents build connected services and hand a verified release to the team.”** The buyer is a small engineering or operations team already using more than one coding agent on the same internal tool. The concrete job is a backend agent exposing a changing API while a frontend agent consumes it, with the human able to see who owns the service, which contract and revision the consumer used, whether the integration call passed, and what version ultimately shipped. This is an inference from the competitive seam, not a finding that customers want a new platform. Coder addresses controlled workspaces and ports, Replit addresses agent building and publishing, and Devin addresses orchestrated sessions; the proposed test asks whether stitching *independent, heterogeneous agents and their live services* is painful enough to justify a separate product ([Coder Agents](https://coder.com/docs/ai-coder/agents), [Replit task board](https://docs.replit.com/features/agent/task-board), [Devin Dynamic Workflows](https://docs.devin.ai/work-with-devin/dynamic-workflows)).

That loop requires more than a task board or a URL registry. The producer's endpoint must have an enforced access boundary and a lifecycle tied to its run. The consumer needs a discoverable service identity, a contract version, and a useful failure when the service stops or changes. The handoff should attach the tested source revisions and actual request/test results. Publication should select an immutable release, check the resulting site and API, and show that they remain available after the producing runs stop. A failed deploy must show failure rather than a green “registered” state. These are proposed acceptance conditions; the current local application does not satisfy them ([Feature spec](/Users/nealkotval/hackgt13/FEATURE_SPEC.md), [Roadmap](/Users/nealkotval/hackgt13/ROADMAP.md)).

The harshest counterargument is that the customer can use GitHub branches and pull requests, a Coder or Codespaces workspace, a shared staging service, and an existing deployment host. Coder already offers organization-scoped ports and shared workspaces, and Railway already resolves private services inside an environment ([Coder workspace ports](https://coder.com/beta-docs/user-guides/workspace-access/port-forwarding/), [Coder workspace sharing](https://coder.com/docs/user-guides/shared-workspaces), [Railway private networking](https://docs.railway.com/networking/private-networking)). If those tools plus a short README remove most of the friction, AgentCloud adds another control plane with little benefit. Heterogeneous-agent support itself also has to create value: if teams standardize on one agent's native delegation, cross-provider orchestration is a corner case. The org-private requirement raises cost and security obligations; it is not automatically a differentiator when existing platforms already offer access controls.

## A small pilot can falsify the thesis quickly

Start with interviews of teams that have recently built an internal site against a separately developed API using two coding agents. Ask them to reconstruct the last handoff: where the API ran, how the other agent found it, what broke when the schema or URL changed, how they verified the combined result, and what remained online afterward. Select a few teams that can show an actual recent project; do not count interest in a hypothetical “multi-agent platform” as demand. Record their current elapsed integration time, manual coordination messages, stale endpoint or schema incidents, and deployment/release steps before running a pilot. These are proposed research measures, not published market data.

Then run the same task through a narrow prototype: one backend run, one frontend run using a different agent, one private API service, one versioned contract handoff, and a human-approved publish to an existing host. Require the frontend to make a real request while both runs are active, verify that an unauthorized client cannot reach the development endpoint, and stop both runs before checking the published site and API. Compare the pilot with each team's ordinary GitHub plus workspace plus deployment flow. Set a go/no-go threshold with the pilot teams in advance; for example, a meaningful reduction in time to the first successful cross-agent request and in manual handoff failures, with no increase in deployment incidents. More persuasive than a polished demo is repeat use on a second real project without founder assistance.

The wedge should be rejected or narrowed if the teams rarely need simultaneous live services, if most friction is contract design rather than service discovery, if endpoint setup costs more time than it saves, or if they prefer to keep release control in their existing CI/CD. A site that nobody needs after the demo also weakens the artifact-home thesis. In that case, AgentCloud can still become a useful coordination layer or integration for Coder and a deployment provider, but the case for owning both compute and hosting would be unproven.

## Conclusion

The next milestone is not “build all the boxes.” It is **demonstrate an integration handoff that existing tools make meaningfully harder**: two independent agents, one changing private service, an evidenced contract, and a release that survives the runs. If teams repeat that flow and can point to saved time or fewer failures, AgentCloud has a plausible product boundary around coordination and promotion. If they cannot, the sensible run/artifact split should remain an internal architecture choice, not the headline claim.
